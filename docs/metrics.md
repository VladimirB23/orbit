# Метрики orbit и SQL за ними

Каждый файл в `backend/src/orbit/domain/sql/` - один шаг расчета с комментарием внутри. Здесь: что он считает,
какой прием использует и почему без него было бы неправильно. Запросы можно гонять руками по копии базы
(функцию `local_day` дает приложение, в DB Browser замени ее на `date(..., 'localtime')`).

## Как это устроено

Сначала строятся временные представления (`CREATE TEMP VIEW`: именованный запрос, живет до конца соединения, в
файл базы ничего не пишет), потом по ним короткие запросы.

```
events -> events_in_force -> lives -> status_changes -> task_facts ------+
                                                     -> milestone_facts  +-> activity_facts -> экран
sessions, commits -------------------------------------------------------+                 -> CSV
```

| Файл | Что получается | Прием | Почему |
| --- | --- | --- | --- |
| `events_in_force` | Журнал без отмененного | `NOT EXISTS`, `UNION` | Отмена - тоже запись. Отмененное и сама отмена не случились |
| `lives` | Рождение каждой строки | `ROW_NUMBER() OVER (PARTITION BY ... ORDER BY id DESC)` | SQLite отдает номер удаленной строки новой: без этого задача получила бы чужую историю (так было с #16) |
| `status_changes` | Все статусы, включая первый | `UNION ALL` | Первый статус лежит в событии другого вида, дальше о нем помнить не надо |
| `task_facts` | Задача с датами пути | `MIN(...) FILTER (WHERE ...)`, `julianday` | Накопительный снимок: одна строка на задачу |
| `milestone_facts` | План и факт этапа | окна по событиям до первого закрытия | План берется таким, каким его знали до закрытия |
| `activity_facts` | Длинный список: день, проект, вид, сколько | `UNION ALL` | Новая мера - еще один `SELECT`, остальное не меняется |

## Запросы экрана

| Файл | Отвечает | Прием |
| --- | --- | --- |
| `totals` | Сколько за период и за прошлый такой же | Два `SUM` с разным `FILTER` за один проход |
| `focus` | Сессии, коммиты, закрытые задачи, последнее движение | `SUM(...) OVER ()` - итог рядом с каждой строкой |
| `expected` | Сколько внимания просит приоритет | `SUM(weight) OVER (PARTITION BY day, kind)`, окно поверх агрегата |
| `activity` | Что было по дням, неделям, месяцам | Рекурсивный CTE строит календарь, `LEFT JOIN` оставляет пустые недели |
| `cycle`, `cycle_stats` | Cycle time, медиана, 85-й процентиль | `ROW_NUMBER` и `COUNT(*) OVER ()`: в SQLite нет `MEDIAN` |
| `plan` | Этапы, закрытые в периоде | Простой `JOIN` по готовому представлению |

Документация: [оконные функции](https://sqlite.org/windowfunctions.html), [CTE](https://sqlite.org/lang_with.html),
[агрегаты и FILTER](https://sqlite.org/lang_aggfunc.html), [свои функции](https://sqlite.org/appfunc.html).

## Определения

- **Сессия** - запись в журнале Obsidian, день начала. Длительность не используется: сессия может висеть открытой
  сутки (ADR 0004).
- **Коммит** - из git папки проекта, все локальные ветки без слияний, по дате автора. Счетчик коммитов в журналах
  сессий неполный: 25.11 у orbit он показывал 19 против 27 в git.
- **Закрытая задача** - статус "готово", день последнего закрытия. Созданная сразу закрытой считается отдельно.
- **Cycle time** - календарные дни от первого "в работе" до последнего закрытия. Нет начала - нет числа.
- **План и факт** - срок, стоявший в журнале до первого закрытия, против дня последнего закрытия.
- **Внимание** - среднее доли сессий и доли коммитов.
- **Ожидание** - каждый день сессии и коммиты делятся по приоритету между проектами, которые уже начались и еще
  идут; коммиты только между проектами с кодом. Меньше половины ожидания - мало внимания, в полтора раза больше -
  много. Нужно хотя бы 10 сессий и коммитов вместе.
- **Движение** - сессия, коммит или смена статуса. Правка сроков и текста движением не считается.
- **Сравнение с прошлым периодом** показывается, только если тогда уже вели записи этого вида.

Когда данных мало, график говорит, чего не хватает: cycle time ждет 10 задач, план и факт - 3 этапа.
