# ADR 0002: правила модели данных

Дата: 2026-11-24 · Статус: принято

## Контекст

PRD задает таблицы и общие правила (статусы, прогресс, просрочки, `events`), но оставляет открытыми
детали, без которых не написать доменный слой: можно ли любые переходы статусов, как считать прогресс
проекта, что именно пишется в журнал, как адресовать записи и что делать при удалении.

## Решение

**Статусы.** Один набор для проекта, этапа и задачи:
`backlog, planned, in_progress, paused, blocked, done, canceled`. `paused` — «сознательно отложено»,
`blocked` — «мешает внешняя причина». Закрытые статусы: `done`, `canceled`.

**Переходы.** Разрешены из любого статуса в любой, как в Linear: жесткий автомат мешает исправлять
ошибки. Побочные эффекты и защита:
- вход в `done` ставит `done_at`, выход из `done` очищает его (у всех трех уровней);
- закрыть этап, проект или задачу с открытыми потомками можно только с `--force`;
- удалить этап с задачами или задачу с подзадачами можно только с `--force`, потомки удаляются тоже.

**Прогресс.**
- задачи: `done / (все - canceled)`;
- этап: по своим задачам (включая подзадачи); без задач — 1.0 если `done`, иначе 0;
- проект: среднее по неотмененным этапам; без этапов — по задачам; без задач — по своему статусу.
  Задачи вне этапов в прогресс проекта с этапами не входят.

**Просрочено:** `due_date < сегодня` и статус не закрыт. «Сегодня» — локальная дата машины.

**Журнал `events`.**
- `create`: одно событие, в `new_value` снимок всех полей в JSON;
- `update`: по событию на каждое реально изменившееся поле, `old_value` и `new_value` как текст
  (даты в ISO, `NULL` если поле очищено). Изменение без разницы событий не пишет;
- `delete`: снимок строки в `old_value`, по событию на каждую удаленную строку (включая потомков);
- архивация — `update` поля `archived_at`;
- производные поля `updated_at` и `done_at` не пишутся: они восстанавливаются из событий `status`.

**Кто изменил.** `actor` берется из `ORBIT_ACTOR` (`vladimir` / `claude` / `system`). Не задана —
`vladimir`, неизвестное значение — ошибка, а не тихая подмена.

**Адресация.** Проект — по `slug` (латиница в нижнем регистре, цифры, одиночные дефисы; совпадает с
папкой в `D:\Projects`). Этапы и задачи — по сквозному числовому `id`.

**Удаление.** Проекты не удаляются, а архивируются (`archived_at`, есть обратная операция). Этапы и
задачи удаляются физически, история остается в `events` (у таблицы нет внешних ключей).

**Время.** Моменты хранятся в UTC (`created_at`, `updated_at`, `done_at`, `events.at`), даты сроков —
как календарные даты без времени.

**База.** Путь из `ORBIT_DB`, иначе `<repo>/data/orbit.db`. Миграции Alembic применяются
автоматически при первом обращении. Режим `WAL`, чтобы чтение (будущий сервер) не блокировало запись
(CLI). Доменный слой делает `flush`, а коммит — у вызывающего: одна команда CLI = одна транзакция.

## Рассмотрели и отказались

- **Строгий автомат статусов** (например, нельзя `backlog → done`): защищает от редких ошибок, но
  мешает правкам задним числом. Опасные случаи закрыты `--force`.
- **Мягкое удаление задач** (`deleted_at`): усложняет каждый запрос ради редкого восстановления;
  снимок в `events` дает то же самое.
- **Прогресс проекта по всем задачам**: этапы без задач (как этапы самого orbit) тогда не влияли бы
  на прогресс.
- **Запись `updated_at` и `done_at` в журнал**: удваивает число событий без новой информации.

## Последствия

- Аналитика (этап 5) строится по `events`: cycle time — по событиям поля `status`.
- Новый статус требует миграции: CHECK-ограничения в схеме, тест это проверяет.
